## 3. CA/Browser Forum hardware key requirement — dates confirmed

- **The requirement date you believed (June 1, 2023) is CONFIRMED**, and the earlier date was **November 15, 2021**. Ballot **CSC-17, "Subscriber Private Key Protection Extension"**, CSBR v3.2, effective **28 October 2022**. Ballot purpose text, verbatim: *"…includes the change of the effective date of November 15, 2021, to June 1, 2023, subscriber key protection and verification requirements in the following sections: Section 6.2.7.4.1, Section 6.2.7.4.2, Section 1.2.2"*. Vote: Yes — DigiCert, eMudhra, Entrust, GlobalSign, Sectigo, SecureTrust; No — HARICA; Yes (consumers) — Microsoft. Source: https://cabforum.org/2022/09/27/ballot-csc-17-subscriber-private-key-extension/ — retrieved 2026-09-16.
- **CSBR "Relevant Dates" table entry** (v3.11.0, dated June 16, 2026), retrieved 2026-09-16 from https://cabforum.org/working-groups/code-signing/requirements/ : `2023-06-01 | 6.2.7.4.2 | Effective June 1, 2023, for Code Signing Certificates, CAs SHALL ensure that the Subscriber's Private Key is generated, stored, and used in a suitable Hardware Crypto Module that meets or exceeds the requirements specified in section 6.2.7.4.1`.
- **Operative text, §6.2.7.4.1 (verbatim, retrieved 2026-09-16):** *"Effective June 1, 2023, Subscriber Private Keys for Code Signing Certificates SHALL be protected per the following requirements. The CA MUST obtain a contractual representation from the Subscriber that the Subscriber will use one of the following options to generate and protect their Code Signing Certificate Private Keys in a **Hardware Crypto Module with a unit design form factor certified as conforming to at least FIPS 140-2 Level 2 or Common Criteria EAL 4+**: (1) Subscriber uses a Hardware Crypto Module meeting the specified requirement; (2) Subscriber uses a cloud-base key generation and protection solution with the following requirements — Key creation, storage, and usage of Private Key must remain within the security boundaries of the cloud solution's Hardware Crypto Module that conforms to the specified requirements; Subscription at the level that manages the Private Key must be configured to log all access, operations, and configuration changes on the resources securing the Private Key; (3) Subscriber uses a Signing Service which meets the requirements of Section 6.2.7.3."*
- **What applied BEFORE June 1, 2023** (same section): non-EV certificates issued prior to 2023-06-01 could use (1) a TPM with key attestation, (2) a suitable Hardware Crypto Module certified to at least **FIPS 140-2 Level 2, Common Criteria EAL 4+**, **or (3) "another type of hardware storage token with a unit design form factor of SD Card or USB token (not necessarily certified as conformant with FIPS 140-2 Level 2 or Common Criteria EAL 4+)"** — i.e. the "any USB token" loophole. EV certificates issued prior to 2023-06-01 already required FIPS 140-2 level 2 or Common Criteria EAL 4+. **So yes: EV had the stricter requirement earlier than OV; the June 1, 2023 date closed the gap for OV.**
- **Signing Services must use a higher grade:** §6.2.7.3 — *"For Code Signing Certificates, Signing Services SHALL protect Subscriber Private Keys in a Hardware Crypto Module conforming to at least **FIPS 140-2 level 3** or Common Criteria EAL 4+."* (retrieved 2026-09-16).
- **§6.2.7.4.2 verification methods** require the CA to ensure hardware generation/storage/use via one of: CA ships a suitable HCM with pre-generated key pairs; subscriber counter-signs requests verifiable by a manufacturer's certificate (**key attestation**) for a key generated in a non-exportable way; CA-prescribed crypto library + HCM; an internal or external IT audit; a report from the cloud key-protection subscription; an auditor-witnessed key pair creation; or an agreement that the subscriber uses a compliant Signing Service. (retrieved 2026-09-16)
- **Corroboration — GlobalSign support advisory:** *"Effective June 1, 2023, a private key should be generated and protected in a FIPS 140‐2 Level 2 or Common Criteria EAL 4+ compliant devices for both Standard and EV CodeSigning Certificates… for Standard CodeSigning Certificate users, the key pair must be generated and stored in a hardware crypto module that meets or exceeds the requirements of FIPS 140-2 level 2 or Common Criteria EAL 4+."* The same page says GlobalSign required compliance **effective April 23, 2023** and requires an audit letter when issuing on HSM. Source: https://support.globalsign.com/code-signing/advisory/new-requirements-related-private-key-protection-codesigning-certificates — retrieved 2026-09-16 (page shows date "Aug 19, 2025"; that appears to be a re-publication date, not the original).
- **Corroboration — Microsoft:** *"As of June 2023, the CA/Browser Forum requires private keys for OV certificates to be stored on a hardware security module (HSM) or hardware token. Most CAs provide a compatible USB token or cloud HSM option."* Source: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options (retrieved 2026-09-16).
- **Corroboration — SSL.com:** OV page states the certificate is issued *"with all ballot resolutions applied. Hardware-backed private keys per the June 2023 key storage mandate for code signing certificates."* (snapshot 2026-09-15)
- **Second corroborating source requested by you could not be read:** `https://securityboulevard.com/2022/05/ca-browser-forum-updates-requirements-for-code-signing-certificate-private-keys/` returned **HTTP 403** on 2026-09-16 → **UNCONFIRMED** (not read).
- **"Deadline by which ALL issued certs must comply" and grandfathering:** the CSBR text I retrieved (v3.11.0) contains **no separate compliance deadline beyond 2023-06-01** and **no grandfathering clause for certificates issued before that date** — the obligation is on the *Subscriber Private Key* being generated/stored/used in a hardware module from 2023-06-01 onward, and pre-existing certificates were not required to be re-issued at that time. Any explicit statement that pre-June-2023 certificates were "grandfathered until expiry" is **UNCONFIRMED** — I found no authoritative wording either way. No extension of the June 1, 2023 date was found (CSC-17 *was itself* the extension from 2021-11-15).
- **Related dates that DO affect multi-year certificate purchases:**
  - CSBR **v3.10, ballot CSC-31 "Maximum Validity Reduction", effective 7 November 2025**; §6.3.2 verbatim: *"For Code Signing Certificates issued before March 1st, 2026, the validity period MUST NOT exceed 39 months. For Code Signing Certificates issued on or after March 1st, 2026, the validity period MUST NOT exceed **460 days**."* (retrieved 2026-09-16)
  - CSBR **v3.11.0, ballot CSC-32**, effective **15 September 2026**: a subscriber certificate must contain exactly one reserved policy OID. (retrieved 2026-09-16)
  - Vendors restate the validity change differently: Sectigo's page says *"Starting February 23, 2026… no longer than 459 days (approximately 15 months). As of February 23, 2026, you will no longer be able to issue a single multi-year Code Signing certificate on a single FIPS-compliant device."* (https://www.sectigo.com/ssl-certificates-tls/code-signing , retrieved 2026-09-16). GlobalSign stopped 2/3-year ordering on **26 December 2025**. The normative CABF statement is **2026-03-01 / 460 days**.
